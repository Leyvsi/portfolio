**Scénario préparé, pas démonstration navigateur déjà validée.** Répéter d'abord la recette autorisée sur une mémoire fictive séparée. Les interactions s'enregistrent réellement dans cette base ; aucun faux compteur. Aucune donnée de remplissage n'est ajoutée au site réel. Les données de test ne survivent pas à l'arrêt du processus.

Le traitement automatique des signalements/propositions et le débannissement ne sont pas livrés.

## Explications simples à mémoriser

- **Mélissa :** « Le HTML présente les champs. JavaScript écoute l'envoi, appelle l'API et met à jour le DOM avec du texte. Nous attendons la confirmation du serveur avant d'annoncer une réussite. »
- **Sylvie :** « Flask reçoit la requête JSON. La session identifie le compte ; les permissions décident de l'accès. Le CSRF accompagne les écritures de la session et ne remplace pas ces contrôles. »
- **Mahamadou :** « SQLAlchemy relie les objets Python aux tables. Le signalement porte l'identifiant du commentaire, protégé par une clé étrangère. Les compteurs proviennent des enregistrements ; nous ne leur attribuons pas de nombres pour la démonstration. »
- **Tous :** « Si la réponse disparaît, la base peut avoir enregistré l'action. Nous n'affichons pas un succès supposé et nous ne renvoyons pas automatiquement. »

À annoncer honnêtement : DOM simulé pour la preuve intégrée, Edge non exécuté à ce jour, SQLite différent de MySQL/InnoDB, sept tests de migration non exécutés, politique complète non publiée, pas de journal persistant ni unicité des signalements. Le script historique donnees.js est exclu des preuves et refusé par le kit ; la couverture de tous les scripts de compte attend une revue distincte. Les décisions humaines RGPD restent ouvertes.
